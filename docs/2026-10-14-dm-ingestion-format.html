DM Ingestion Format

The record

There is no new format. Every importer already emits one JSON object per line, and the extension imports any object that has a url. A DM link uses that record and adds three optional fields. Fields the extension does not know are stored untouched.

FieldMeaning
urlcanonical link, required
kindreel, ig-post, tweet, page
textcaption or page text
authorname and handle
saved_atwhen the DM was sent
viaimporter name
accountnew: account folder
threadnew: list of threads
sendersnew: each distinct sender, you once

The existing fields keep their names: saved_at, not sent_at, and via, not source. via takes instagram-export, x-archive or chrome-agent. A record with text is what lets a later import upgrade a bare one.

A link seen in several threads is one record whose thread lists all of them. The importer builds that list, as instagram.py already does when it dedups on the canonical URL. The extension keeps the first record per URL, so a later import that adds a thread will not update a record that already has text.

Browser agent tiers

The archive and export routes are the baseline. A browser agent is a fallback that produces the same records, and each run needs your approval first: it drives your logged-in accounts, so the count of pages is stated up front and the first captcha or challenge ends the run. Chrome would also need those accounts logged in.

  1. Plain external links (a DM that contains a news article or a tweet): the agent returns URL<TAB>YYYY-MM-DD lines. The enrich-x.py and enrich-web.py scripts resolve them with no login. Both read only the first two columns, so the account and thread cannot ride along; use tier 2 when they matter.
  2. Login-walled Instagram posts and reels, and any link where the account and thread must be kept: the agent returns full records with via: "chrome-agent", plus account, thread and senders.

Where refresh changes

All of this is in tools/refresh.zsh. Nothing is built yet.

  • Configuration: config.local.sh gains an associative array of accounts, for example IG_ACCOUNTS[main]="thread_a thread_b". INSTAGRAM_EXPORT_DIR becomes a parent whose subfolders are the accounts. config.local.sh.example documents it.
  • Discovery: today a single loop over instagram-*(Nom) picks one newest valid export and stops. It becomes a loop over the account folders, one newest export each.
  • Instagram: instagram.py takes an account and its thread allowlist, returns several threads where it now returns the first self-thread, and gains --list-threads sorted by link count so you can fill the allowlist.
  • Merging: step 5 concatenates the source files by name, and the order decides which record wins. The X DM importer gets its own file and a line there. Its output cannot go through the worklist, which loses the account and thread.
  • X archive: the importer reads the DM file of a real archive. It is written after you request the archive and I have read its actual layout.

Still unchecked

  • The layout of the X archive's DM files. I recall direct-messages.js and direct-messages-group.js, with t.co links whose expanded URL is missing in older archives. That is memory, and no fixture exists.
  • Whether DM links in other people's Instagram threads use the same share.link shape as the self-thread.
  • Whether the cards face and telegram-messages-to-html.py ignore the new fields, and which kind a DM link to an ordinary site should get. Today the enrichers use page.
  • Where the account would be shown. Nothing renders it today, so the field is stored and unseen until the viewer is changed.
